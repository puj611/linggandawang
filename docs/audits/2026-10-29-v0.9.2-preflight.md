## 1 问题清单（按严重度降序）

### [高][B·安全] 「密钥不出前端」的安全承诺在流式路径与 4 处 engine 上不成立

**位置**
- `src/stores/apiKeyStore.ts:101-109` —— `getApiKey()` 直接 `invoke('load_api_key')` 拿回明文
- `src-tauri/src/commands/api_key.rs:37-47` —— `load_api_key` 把明文返回给前端
- `src/lib/llm/openai-adapter.ts:293-341` —— `chatStream` **不走 Rust 代理**，直接 `headers.Authorization = Bearer ${apiKey}`
- 4 处 engine 调用 `getApiKey()`：`ImagePromptExtractor.ts:109`、`LLMIntentAnalyzer.ts:100`、`RequirementSyncer.ts:52`、`SmartFollowup.ts:197`

**证据**
```ts
// openai-adapter.ts:332-334 —— 流式路径明文注入
if (!isLocal && apiKey) {
  headers.Authorization = `Bearer ${apiKey}`;
}
```
```rust
// llm_proxy.rs:5 注释宣称
// 安全目标：1. 前端不再持有明文 API Key —— Rust 从 keyring 读取并注入
```
两处直接矛盾。

**触发路径**：任意走 `chatStream` 的调用（或 engine 的 4 个模块）→ `useApiKeyStore.getState().getApiKey()` → `invoke('load_api_key')` → 明文进入 JS 堆 → 若走流式则再放进 fetch header。

**最坏影响**：WebView 内任何 XSS/恶意依赖（本项目用 @huggingface/transformers 这类第三方库）可直接读 `window` 上/闭包里的明文 key；一旦前端被攻破，keyring 这层保护形同虚设。这是本项目宣称「密钥进系统 keyring，数据不出机器」的核心卖点。

**修复建议**（成本 中）
1. **流式也走 Rust 代理**：给 `llm_proxy_chat` 增加 `stream: bool`，用 Tauri event 把 chunk 推回前端；或在 `llm_proxy` 加 `llm_proxy_chat_stream`。这是根治。
2. **移除 `load_api_key` 的明文返回**：改为 `has_api_key(provider) -> bool`（只回存在性），前端 UI 只需知道「是否已配置」。删除 `getApiKey()` 对外暴露。
3. 过渡期至少在 `getApiKey` 加注释标明「仅供必须直连的场景，勿扩散」，并把 engine 4 处改为不传 key（走 proxy）。

### [高][E·架构] 分层约束被 4 处 engine 反向依赖 stores 破坏

**位置**：`src/engine/{ImagePromptExtractor,LLMIntentAnalyzer,RequirementSyncer,SmartFollowup}.ts`

**证据**
```ts
// engine/LLMIntentAnalyzer.ts:100
const apiKey = await useApiKeyStore.getState().getApiKey();
```
`AGENTS.md` 分层约束明确：**引擎层（engine）纯业务逻辑，不依赖 Tauri API / React**；实测基线记录 `src/lib → engine/stores` 为 0 处，但 **engine → stores 这一反向没有纳入基线检查**。

**触发路径**：engine 被 MCP server 复用（`mcp-server/tools.ts` 已 import QuestionEngine/QuestionLoader/PromptGenerator）。若某天 MCP 侧调用到 `LLMIntentAnalyzer`，会连带拉起 zustand + Tauri invoke，在纯 node 环境直接崩。

**最坏影响**：MCP server 打包体积已 517KB（含引擎链）；engine→stores 的耦合让「引擎可独立测试/独立复用」这个架构承诺失效，也是上一条安全问题的根因。

**修复建议**（成本 中）：engine 不自行取 key，改为**由调用方（hooks）注入已配置的 adapter**；engine 只依赖 `LLMAdapter` 接口类型。这与「引擎层不依赖 Tauri」一致，同时天然消除上一条的 4 个泄露点。

### [中][B·安全] `load_api_key` 缺速率/审计，且 service 名固定可枚举

**位置**：`api_key.rs:37-47`；`llm_proxy.rs:13`、`api_key.rs:4`（`KEYRING_SERVICE = "linggandawang"`）

**证据**：provider 白名单校验有（`ALLOWED_PROVIDERS`），但同一渲染进程内可无限次调用 `load_api_key` 拿任意已存 provider 的明文；`llm_proxy.rs` 的 `ALLOWED_PROVIDERS` **比 `api_key.rs` 多一个 `"local"`**，两处白名单不一致。

**最坏影响**：若前端被攻破，攻击者可直接枚举 4 个 provider 抽干所有密钥（含用户从没在 UI 里配过的）。

**修复建议**（成本 低）：统一两处 `ALLOWED_PROVIDERS` 常量到一处；`load_api_key` 改存在性查询（见高危第 1 条）。

### [中][A·Bug] `sanitize()` 对非 ASCII 文本可能 panic

**位置**：`llm_proxy.rs:143-144`

**证据**
```rust
out.push(without_bearer[i..].chars().next().unwrap());
i += without_bearer[i..].chars().next().unwrap().len_utf8();
```
`i` 是**字节**索引。当 `bytes[i]` 落在多字节 UTF-8 字符内部时，`without_bearer[i..]` 会 panic（`byte index is not a char boundary`）。当前 `i` 只在 `sk-` 分支里跳过 ASCII 字母数字，其余路径 `i += len_utf8()` 保持边界——但前提是**从未有分支把 i 推进到非边界**。审查确认逻辑正确，属**潜在脆弱点**而非现网 bug。

**最坏影响**：若将来有人改 `sk-` 分支的跳过范围（如允许 `_` 或 `-`），中文字符处即 panic，整个 LLM 调用链崩溃。

**修复建议**（成本 低）：改用 `char_indices()` 迭代，或先转 `Vec<char>`。并在测试里补一条「中文 + sk- key 混合」用例。

### [中][B·安全] CSP 与 `debugReporter` 的开发期外发通道

**位置**：`src/lib/debugReporter.ts:6`（`http://127.0.0.1:7777/event`）；`capabilities/default.json`（`core:default` 覆盖面）

**证据**：`debugReporter` 有 `if (!import.meta.env.DEV) return;` 短路，生产无外发 —— 这点做对了。但：
- 文件注释写「会话结束后会与本文件一起清理」，而**它仍在仓库里且被 `useFlow.ts` import 了 6 处**（`#region debug-point`）。死代码长期留存，未来若有人误删 `import.meta.env.DEV` 判断即变成生产外发。
- `capabilities/default.json` 用 `core:default`（较宽），叠加 `sql:allow-execute`，渲染进程有完整 SQL 写权限（虽限单库）。

**最坏影响**：调试通道残留 + 宽权限叠加 = 前端被攻破时的数据外发面。

**修复建议**（成本 低）：发布前删除 `debugReporter.ts` 与 `useFlow` 内 6 处 `#region debug-point` 插桩；`capabilities` 把 `core:default` 收窄为显式列出的 core 权限。

### [低][B·安全] `image.rs` 白名单逻辑方向反了

**位置**：`image.rs:59-78`

**证据**
```rust
if !is_in_user_scope(&canonical) {
    const BLOCKED_PATHS: &[&str] = &["windows\\system32", ...];
    for blocked in BLOCKED_PATHS {
        if path_str.contains(blocked) { return Err(...); }
    }
}
```
**在用户目录外**才做黑名单检查；**在用户目录内则完全跳过**。而用户目录（`USERPROFILE`）下恰恰放着 `.ssh`、`.aws`、`.npmrc` 等 —— 这些靠 `is_sensitive_file(file_name)` 兜（按文件名/扩展名）。但 `is_sensitive_file` 只匹配**文件名段**，无法拦住 `C:\Users\x\Documents\my-passwords.txt` 这类任意文件。

**最坏影响**：渲染进程可读用户目录下任意 ≤10MB 的非敏感命名文件并转 data URL 外发（配合恶意前端 = 数据窃取）。

**修复建议**（成本 低）：改为**正向白名单**——只允许用户通过 `dialog:allow-open` 显式选中的文件（记一次授权签名，类似 `project.rs` 的 `assert_authorized` 范式）。

### [低][C·质量] `chatStream` 与 `chat` 的 SSRF 校验强度不一致

**位置**：`openai-adapter.ts:300`（`chatStream` 只调前端 `validateBaseUrl`）vs `chat`（Tauri 下走 Rust `validate_ssrf` 含 DNS 解析）

**证据**：前端 `validateBaseUrl` 注释自认「不做 DNS 解析（轻量方案），DNS 重绑定需 Rust 代理方案彻底解决」。而 `chatStream` 恰好**没有** Rust 代理，即 DNS 重绑定防护在流式路径上缺失。

**最坏影响**：攻击者控制的域名解析到内网地址 → 流式请求打到内网服务（SSRF）。

**修复建议**（成本 中）：与高危第 1 条一并解决（流式走 Rust 代理后自动获得 DNS 校验）。

---

### [低][D·性能] `llm_proxy` 每次请求新建 `reqwest::Client`

**位置**：`llm_proxy.rs:172-176`、`:215-218`

**证据**：每次 `llm_proxy_chat` 都 `Client::builder().build()`，丢弃连接池。高频意图分析（8s 超时、多轮）下反复 TLS 握手。

**修复建议**（成本 低）：用 `once_cell::sync::Lazy<reqwest::Client>` 复用，仅对 timeout 差异大的场景建两个池。

## 3 亮点

1. **SSRF 防护做到了边界级**：`is_private_ip` 覆盖 CGNAT 100.64/10、IETF 192.0.0/24、198.18/15、203.0.113/24，且 **IPv4-mapped 先 `to_ipv4_mapped()` 还原**、**NAT64 64:ff9b::/96 整体拒绝** —— 这两条是真实绕过手法，且有对应单测锁死。
2. **密钥脱敏双形态**：`sanitize()` 同时处理 `Bearer xxx` 与裸 `sk-xxx`，且不会误伤 `task-scheduler-xx`（有测试）。
3. **项目扫描有真实授权模型**：`project.rs` 的 `assert_authorized` 用 canonicalize 比对，且被 `scan_project`/`full_scan_project`/`scan_file_tree_cmd` 等多命令共享 —— 这是本项目安全设计最好的一处，可作为修 `image.rs` 的范式。
4. **凭据零落盘**：keyring-only，导出功能双向剔除密钥（键名+值形状扫描），实测零残留。
5. **LLM 超时可回收**：`tokio::time::timeout` 包裹 reqwest，避免占住 worker 120s；前端用 race + `finally cleanupAbortListener` 清残留监听器。

## 6 沉淀建议（待用户确认后写入 AGENTS.md）

19. **「安全承诺」必须与实际调用路径逐条对齐**（本次发现）：`llm_proxy.rs` 注释宣称「前端不再持有明文 API Key」，但 `load_api_key` 命令仍返回明文，且 `chatStream` 与 4 处 engine 都调 `getApiKey()`。写安全注释时必须在**每个调用方**核实，否则注释本身成为虚假安全信号。
20. **audit 的范围要覆盖 Rust 侧**（本次发现）：`npm audit` 只覆盖 JS；`cargo audit` 未安装，RustSide 依赖（reqwest/tokio/keyring）的 CVE 从未检查过。CI 应补 `cargo audit`。
21. **白名单逻辑要检查「何时跳过」而非只看「何时拦截」**（`image.rs`）：`if !is_in_user_scope() { 黑名单检查 }` 的结构意味着用户目录内**完全不做路径限制** —— 审查白名单时要问「哪些输入走了旁路」。
